# Native test vectors — canonical bytes and passkey challenges

Machine-generated by `scripts/native-vectors.mts` (`npx tsx scripts/native-vectors.mts` from the repository root) with the
**real** TypeScript canonical functions of this repository, at commit `52e513b` + worktree `native-clients`. A native client
(Swift) must reproduce `canonicalHex` and `hashHex` byte for byte from `object`.

Each `SPW-<DOMAIN>.json` is a JSON array of

```json
{ "name": "...", "domain": "SPW-…-v1", "source": "<TS path> <exported function>", "object": { … }, "canonicalHex": "…", "hashHex": "…" }
```

- `object` — the object as JSON, as the API serves it (it went through `JSON.parse(JSON.stringify(…))`).
- `canonicalHex` — hex of the canonical bytes. Present in **every** vector of this set.
- `hashHex` — hex of `SHA-256(canonical bytes)`. The WebAuthn challenge is these 32 bytes (base64url, no padding, in
  `options.challenge`). Exception: `SPW-ORDER-INTENT-v1`, `SPW-ORDER-BODY-v1`, `SPW-TRADING-MANDATE-v1` and
  `SPW-QUOTING-SECTION-v1` hashes are never a challenge by themselves (§4).

The generator is deterministic (fixed UUIDs and timestamps, no clock, no randomness, no network, no database query): two runs
give identical files. It asserts for every vector that `sha256(canonicalHex) == hashHex` where `hashHex` comes from the real
hash function, and that the bytes start with the domain string.

## 1. The three serializations

### 1.1 Framed (name, value) pairs — "F"

Used by 21 domains. One implementation, copied in several files (`intent.ts:160-171`, `nft-intent.ts:78`, `mandate.ts:47-49`,
`canonical.ts:26`, `collateral.ts:156`, `gmx.ts:468`, `cctp-sol-tx.ts:165`); all byte-identical in behaviour.

```
bytes = UTF8(domain) || 0x00 || for each (name, value) in the FIXED order of the code:
          u16 big-endian (byte length of UTF8(name)) || u32 big-endian (byte length of UTF8(value)) || UTF8(name) || UTF8(value)
hash  = SHA-256(bytes)
```

- The separator after the domain is **one zero byte**. No terminator at the end. Lengths are **byte** lengths of the UTF-8
  encoding (vectors with `é`, `—`, `«»`, `°` are included), header = 2 + 4 bytes, both **big-endian**, name length first.
- Field order is fixed by the code, **never** by JSON key order.
- Value stringification (every value is a string before framing):
  - **string**: as is (no trimming, no case change; EIP-55 addresses keep their case).
  - **integer number** (`v`, `decimals`, timestamps, nonces, counts…): decimal digits, no sign, no leading zero, no exponent
    (`String(n)` of a safe integer). `v` is always `"1"`.
  - **boolean**: `"1"` / `"0"`.
  - **base-unit amounts** (`amount`, `maxFee`, gas values…): already decimal strings in the object; framed as is.
  - **decimal string** `canon(x)` (prices, sizes, USD amounts of the derivatives/trading objects — marked *canon* below): remove
    trailing zeros of the fraction, then remove a trailing `.`; a zero value is `"0"`. The integer part is untouched; never an
    exponent. `"2500.50"→"2500.5"`, `"25000.000"→"25000"`, `"68500.0"→"68500"`, `"0.00"→"0"`, `"0.0000123400"→"0.00001234"`.
    (`packages/derivatives/src/decimal.ts:34-73`, `D.str(D.from(x))`.) The object served by the API may or may not already be
    canonical: always apply it.
  - **null** (where the schema allows it): the **empty string** `""` — the pair is still present.
  - **absent optional field**: per domain, either the pair is **absent**, or (only `gmx.orderKey`) present with `""`. Stated per
    domain below.
  - **lists**: per domain — either expanded (`*.count` + indexed names, order kept), or sorted and joined with `,`.
  - **maps**: expanded to one pair per key, keys sorted.
- **Sorting** is JavaScript's default: by UTF-16 code unit, ascending, no locale. For ASCII this is plain byte order:
  digits < upper case < `_` < lower case; `.` < digits. (Vector `synthetic-x-map-key-sort-order`: `A, B, a.1, a1, aB, a_1, ab, b`.)
  In Swift: `sorted { $0.utf16.lexicographicallyPrecedes($1.utf16) }`, never `localizedCompare`.

### 1.2 Canonical JSON — "J"

```
bytes = UTF8(domain + "\n" + J(object))          hash = SHA-256(bytes)
```

`J` = JSON with **object keys sorted at every depth** (same UTF-16 code-unit order), **no whitespace**, arrays in their own
order, and every scalar written as JavaScript's `JSON.stringify` writes it:

- strings: `"` → `\"`, `\` → `\\`, U+0008 `\b`, U+0009 `\t`, U+000A `\n`, U+000C `\f`, U+000D `\r`, any other code unit below
  U+0020 → `\u00xx` (4 hex digits, **lower case**); everything else **raw UTF-8**: `/` is NOT escaped (Swift's `JSONEncoder`
  /`JSONSerialization` write `\/` unless `.withoutEscapingSlashes`), U+007F raw, non-ASCII raw (not `\uXXXX`), emoji raw;
- `null`, `true`, `false`;
- numbers: integers as plain digits. Non-integers occur in ONE place (`SPW-APIKEY-INTENT-v1` `limits.*NotionalUsd`): the
  shortest round-trip form of ECMAScript (`2500.5`, `0.1`, `100000000`) — an integer-valued double has **no** `.0`.
- a key whose value is `undefined` does not exist in JSON; the object you receive has no such key. (Difference between the
  two server implementations, not visible on the wire: `stableJson` of `exec.ts:151` would write an explicit `undefined`
  member as `null`, `canonicalJson` of `key-model.ts:30` drops it. No such member is produced by the code read.)

Vectors `release-kill-switch-engaged-by-owner` and `…-control-chars` exercise the escaping rules.

Advice: re-serialize the JSON tree you received (keep integers as integers; do not round-trip amounts through `Double`).

### 1.3 Line-joined — "L"

```
bytes = UTF8(parts joined with "\n")  (the domain is the first part; no trailing newline)      hash = SHA-256(bytes)
```

## 5. One domain string, several meanings — read this before grepping

- **`SPW-INTENT-v1`** is serialized in exactly ONE place: `packages/core/src/intent.ts:105/160`. Its occurrence in
  `packages/core/src/nft-intent.ts:7` is a comment ("the transfer intent … is not touched"). NFT objects have their own
  domains and their own field lists; only the framing is shared.
- **`SPW-MANDATE-v1`** is serialized in exactly ONE place: `packages/core/src/mandate.ts:47` (the spot vault mandate). Every
  other occurrence is a *label*, not a serialization: `packages/trading/src/mandate/trading-mandate.ts:6` (comment), `:333`,
  `:336`, `:460`, `:504`, `:624` (the value of a `shape` tag / a table of signer shapes), `services/api/src/agents/mandate-write.ts:3`
  and `agents/runtime-routes.ts:54` (comment / shape tag).
- **`SPW-VENUE-MANDATE-v1`**: one serialization (`derivatives/src/live/mandate.ts:73`); elsewhere a `shape` tag — including
  the string value `signer.shape` INSIDE the `SPW-TRADING-MANDATE-APPROVAL-v1` intent, where it is hashed as data.
- **`SPW-VENUE-QUOTING-MANDATE-v1`**, **`SPW-TRADING-MANDATE-v1`**, **`SPW-QUOTING-SECTION-v1`**: one serialization each;
  the other occurrences are constants, shape tags, comments or SQL comments (`services/api/src/db.ts`).
- **`SPW-ORDER-INTENT-v1`** also appears in `services/api/src/trading-api/spec.ts:166` and the generated SDK
  (`packages/trading-sdk/src/generated/openapi.ts:102`) as documentation text.
- **`SPW-ENROLL-v1`**: two independent copies of the same one-liner (API `auth.ts:16`, signer `signer.ts:598`).
- **Two JSON canonicalizers** share the "J" format: `stableJson` (`exec.ts:151`, private) and `canonicalJson`
  (`key-model.ts:30`; a third private copy in `agent-runtime/model.ts:192`, a client copy in `packages/trading-sdk/src/util.ts:10`).
  They agree on every value that can travel as JSON.
- Seconds vs milliseconds: intents, NFT objects, mandates, authorizations use unix **seconds** for `createdAt`/`expiresAt`;
  `SPW-VENUE-ORDER/LEVERAGE` `nonce`/`expiresAt`, `approveNonce`, `VenueWithdrawal.time`, canonical orders and every "J"
  intent stamp use **milliseconds**. Irrelevant for the bytes (digits either way), relevant for display.
