### 4. Semantics common to both SDKs

- **Construction**: key from the argument or `SP_WALLET_API_KEY`; base URL from the argument, `SP_WALLET_BASE_URL`, or
  `https://wallet.spboucher.ai`; `http://` refused except for localhost; user agent `sp-wallet-<lang>/<version>`.
- **Errors**: `ValidationError` (400, 422), `AuthenticationError` (401), `PermissionDenied` ⊃ `ScopeDenied`
  (`insufficient_scope`; `scope_denied` is mapped too), `MandateRequired`; `NotFound`; `Conflict` ⊃
  `IdempotencyConflict`, `AmbiguousSymbol` (with `candidates`); `RateLimited` (retry-after); `NotImplementedError` ⊃
  `ExecutionNotWired`; `ServerError` ⊃ `ServiceUnavailable`; `NetworkError` ⊃ `TimeoutError`; `OutcomeUnknown`;
  `WaitTimeout`; `WebhookVerificationError`; `ConfigurationError`. Each carries code, message, status, request id.
- **Retries**: as documented in `docs/sdk/*.md`. One decision goes beyond the brief and is deliberate: after a mutating
  attempt that ended without an answer, a later 401 / 403 / 429 / 5xx is **also** `OutcomeUnknown`, because the server
  decides those before it looks at the `Idempotency-Key` — they say nothing about whether the first attempt ran.
  A single 500 / 502 / 504 on a mutating call is `OutcomeUnknown` too; a 503 carrying an API code is
  `ServiceUnavailable`.
- **Pagination**: the API has none (no cursor, no offset). No helper was written; both documents say so.
- **`wait_for_order`**: final = FILLED, CANCELLED, REJECTED, FAILED; UNKNOWN keeps waiting; a timeout raises
  `WaitTimeout`, which says the order has not failed.
- **`notional_usdc` / `notionalUsdc`**: the contract sizes an order with `size` only. To keep the quick-start example
  of the brief, both SDKs accept a notional as a **client-side** convenience: they read `GET /markets/{instrument}` and
  send `size = floor(notional / mark, lot size)` in exact arithmetic, and refuse a stale or missing mark. No field was
  added to any request.

## Mismatches between the OpenAPI document and the real server

Found by running both SDKs against the real route handlers. None of them was worked around silently.

1. **Members sent in objects the document declares closed** (`additionalProperties: false`), found by validating every
   real answer against its schema: `GET /portfolio` sends `totals.note`; `GET /balances` sends a top-level `halted`.
2. **Money as JSON numbers.** The document's description says "Numbers that carry money are decimal strings", but
   `GET /portfolio` declares and sends `wallet.valueUsd`, `wallet.balances[].valueUsd` and `totals.walletUsd` as JSON
   numbers. The TypeScript types say `number` (as documented); the Python SDK parses them as `Decimal`.
3. **422 is not declared.** `GET /markets/{symbol}/orderbook` answers `422 no_orderbook` for GMX and spot ids (observed),
   and `venue_rejected` is a 422 too. No operation of `trading-v1.json` lists a 422 response; only the Markdown error
   table does.
4. **404 codes.** The Markdown table lists `unknown_market`, `unknown_order`, `not_found`. Observed: `unknown_venue`
   and `unknown_instrument` (and `unknown_order`); no code path of the read side produces `unknown_market`.
   `GET /markets?venue=nowhere` answers `404 unknown_venue` although `listMarkets` declares no 404.
5. **Unknown route under `/api/v1/trading/`** without `SPW_WEB_DIR`: Fastify's own body
   `{"message":"Route … not found","error":"Not Found","statusCode":404}` — `error` is not a machine code there. The SDKs
   map it to `NotFound` with the code `http_404`.
6. **No success schema for the 12 write operations** (only the 501 is declared). The SDKs cannot type their answers.
7. **Order `status` is an open string.** The read side reports the older vocabularies (`pending`, `open`, `filled`,
   `partially_filled`, `cancelled`, `rejected`, `triggered`, live `state` values, GMX operation states, agent swap
   states), not the twelve states of the unified machine, and `final` is `null` for agent swap orders. Consequence:
   `wait_for_order` on such an order relies on `final`, and never ends by itself on an agent swap order (it ends with
   `WaitTimeout`). The document should carry the enum once the state machine is wired.
8. **`mandateId` is not checked at key creation**: a key created with a random UUID as `mandateId` passes the
   `mandate_required` gate and reaches the write handlers (it is how the tests reach the 501 on every write). Harmless
   while execution answers 501; it must be validated before execution is wired.
9. **Lot size is not in the contract.** `GET /markets/{symbol}` declares `instrument` as a free-form object; the real
   answer carries `lotSize`, `tickSize`, `minOrderSize`. Sizing an order correctly needs them: they should be declared
   (or the order request should accept a notional).
10. **`StartRequest.agentId` on `POST /agents/{id}/start`**: the shared body lets a second agent id be sent next to the
    one in the path. The Python SDK does not expose it on `start_agent`.
11. **No pagination** on `orders` and `activity` (only `limit`, at most 500): older rows cannot be reached.
12. **`idempotency_conflict` cannot be observed with a key today**: a 501 is not stored, so the same key with another
    body answers 501 again (observed). The SDKs' handling of the 409 is covered by unit tests only.

Naming note, not a server bug: the brief names the scope refusal `scope_denied`; the server and its document say
`insufficient_scope`. Both are mapped to `ScopeDenied`.

## Limitations

- The write path is exercised against the real server only up to the 501 (and the 403 `mandate_required`). Success
  answers, replays (`Idempotent-Replay`) and `idempotency_conflict` are covered with a mocked transport.
- `OutcomeUnknown` and retries are covered with a mocked transport (a real timeout of a write cannot be provoked on a
  server that answers 501 immediately).
- The integration tests depend on PostgreSQL (skipped otherwise) and, for market data, on the venues' public
  endpoints (the affected test is skipped when a venue is unreachable).
- In the Python integration test the `limited` key (3 calls a minute) is shared by the sync and the async runs: the
  second run usually meets the limit at once (`remaining []` in the transcript); the countdown 2, 1, 0 is asserted
  by the first.
- Neither package is published; both are installed from the repository path.
- No static type checker (mypy / pyright) is configured for the Python SDK: ruff and the tests only.
