# SP Trading API — security model (V11)

Scope of this document: the machine-authentication layer on branch `v11-trading-api`. Architecture:
`docs/TRADING-API-ARCHITECTURE.md`.

## 1. The statement that matters most

**The isolated signer authenticates the API as a whole.** One shared HMAC secret opens the signer to the API process
(`docs/V11-AUDIT.md` §7, "Design"). The signer cannot tell the owner's session from an agent or from an API key, and
it never sees a scope.

Consequences:

- A scope is access control **inside the API**. It does not survive a compromise of the API process.
- When execution is wired, what a key can make the signer sign must be bounded by a **mandate the signer enforces
  itself** (instruments, notional, leverage, loss floor, expiry). Never by the scope alone, and never by the key's
  `limits` alone: those are checked by the API.
- The passkey approval of a key (section 4) is verified by the API, not by the signer. It protects against a stolen
  session. It does not protect against a compromised API process, which could insert a key row directly.

Since Phase F a key can execute: paper orders under a paper mandate, and — with `SPW_TRADING_API_EXECUTION=on` on the
server — live Hyperliquid orders under a live mandate the signer enforces. What bounds a stolen key, the confused-deputy
analysis and the items for review are in `V11-SECURITY-REVIEW.md`, section "Execution through the trading API".

## 2. What a key can reach

A key principal reaches `/api/v1/trading/*` and nothing else. This is enforced three times:

1. `apiKeyGate` (onRequest): a request carrying `Bearer spw_live_…` on any other path is refused with 403
   `key_path_forbidden` before the key is looked up.
2. `scopeGuard` (preHandler): a key principal on a route whose pattern is outside the prefix is refused, even if the
   gate were bypassed. A trading route without a declared scope is closed to every principal.
3. Each `/api/v1/developer/*` handler checks `principal.kind === 'owner'`.

There is no scope for keys, the recovery phrase, signer administration, security settings, API-key management or
mandate approval. The scope enum is closed (`spec.ts`).

Test: `trading-api.test.ts` enumerates every route of the Fastify instance (more than 190) and calls each one outside
the prefix with a valid key holding every scope and a mandate id; each answers 403.

## 3. Why HMAC with a pepper, not scrypt

| Requirement | HMAC-SHA-256 + pepper | scrypt |
|---|---|---|
| Cheap verification on every request | one HMAC (microseconds) | tens of milliseconds and memory per request; a denial-of-service lever |
| Resists database theft | the secret is 256 random bits: no dictionary exists, with or without the pepper | same, at a cost that buys nothing for a random secret |
| Resists an attacker who can write to the database | he cannot forge a valid hash without the pepper | he can insert a hash of a secret he chose |

A slow hash protects low-entropy secrets. These secrets are 32 random bytes generated by the server, so the slow hash
adds cost and no protection. The pepper adds the third row: a database write does not create a working key.

The pepper is in `trading-api-secrets.json` (mode 0600, directory 0700, outside the database and outside its nightly
backup) or in `SPW_API_KEY_PEPPER`. The comparison is constant-time; an unknown key id costs the same HMAC.

## 4. Threats

| Threat | What limits it | What remains |
|---|---|---|
| **Key theft** (leaked from a client machine or repository) | required expiry (≤ 1 year); scopes; source-address list; venue, instrument and network restrictions; per-key rate limit; immediate revocation; usage log by route and status; `key.revoked` webhook. Execution scopes are inert without a mandate. | A thief reads whatever the key's read scopes allow until revocation. Without a source-address list nothing ties a key to a machine. |
| **Replay** of a captured request | TLS in front of the API. Mutations require `Idempotency-Key`: the same request returns the stored answer and is not run again; a different request under the same key is a 409. Optional `X-SPW-Timestamp` (±300 s). | The timestamp is optional and not signed: it stops stale retries, not an attacker who holds the key. There is no per-request signature. Idempotency records last 24 h. |
| **Scope escalation** | closed enum; the guard reads the scope from the route's own config; widening a key needs a passkey assertion over the canonical change, recomputed against the key as stored; an intent is single-use and bound to one key. Refusals are audited (`apikey.denied`). | A stolen owner session can narrow, revoke or list keys, and create webhooks, without a passkey. It cannot create, rotate or widen. |
| **Confused deputy** between the owner session and a key | a key request skips the CSRF and Origin check only because a bearer token is never attached by a browser on its own; a request with a key **and** the session cookie is refused, so the cookie cannot ride the CSRF-exempt path. The owner session on trading routes keeps the CSRF check. Idempotency namespaces are per principal. | The audit actor of existing routes is still the literal `owner` in most call sites; the principal is available (`actorOf`) but not threaded through them. |
| **Log leakage** | the usage log stores the route pattern, never the URL, query string, body or headers; Fastify redacts `authorization` and `cookie`; the secret is returned once and never stored; audit events carry key ids and settings only. Tests search the database for the secret. | The key id is public by design. Reverse proxies in front of the API log on their own terms. |
| **Database theft** | hashes are HMACs of 256-bit secrets under a pepper that is not in the database; webhook signing secrets are in the secrets file, not in the database | The dump reveals key names, scopes, restrictions, usage history and webhook URLs. |
| **Brute force of a secret** | 256 bits; 10 failed authentications per minute per address, then 429; one answer for every failure reason | The throttle is per process and in memory. |
| **Webhook abuse** (data sent to an attacker's URL) | https only, no credentials in the URL, no redirect; payloads hold identifiers and states only; creation is audited; at most 10 endpoints | Creation needs the session only. The URL host is not checked against private address ranges. |

## 5. Things a reviewer should know

- `mandate_id` on a key is a stored UUID. Nothing verifies that the mandate exists, is approved or is active.
  The check `mandate_required` only tests that the column is set. The real check must be added with execution.
- `orders:cancel` is treated as an execution scope and needs a mandate. A cancel reduces risk; the integrators may
  decide to relax it, in line with the audit's rule that a reduction is never blocked.
- Key limits (`maxOrderNotionalUsd`, `maxDailyNotionalUsd`) are recorded and not enforced.
- Limiters and the failed-auth throttle are in memory: several API processes would each count separately.
- The WebAuthn counter of the API's credential copy is updated on a key approval, as it is on login. The signer keeps
  its own counter.
- Rotation creates a new key id. Clients that store the id must update it.
- No real order or transaction was sent during this work; the end-to-end runs used a throwaway local stack with
  broadcast off.
